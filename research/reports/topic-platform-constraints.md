# macOS platform constraints for cleanup and uninstall

Task T-0010, by topic-platform-constraints, 2026-09-23. Test machine: macOS 26.6 (25G72), Apple silicon, SIP and Authenticated Root enabled (`csrutil status`, `csrutil authenticated-root status`), Xcode SDK MacOSX26.5.

Status labels: **verified-locally** means reproduced on this Mac. **sourced** means taken from a cited Apple document, WWDC session or DTS forum answer, or from a third-party write-up where marked. **unverified** means not checked.

## Summary

1. **Apps in `/System/Applications` cannot be removed.** They live on the Signed System Volume, which is sealed and mounted read-only, and they carry the SIP `restricted` flag. `/Applications/Safari.app` is a restricted symlink into the App cryptex. What is honest to offer: removing Apple's App Store apps in `/Applications` (GarageBand, iMovie, Pages, Numbers, Keynote, Xcode) plus their large content libraries, and reporting the built-in apps as "part of macOS, protected". A "remove Mail/Chess" feature would need SIP and Authenticated Root disabled from recoveryOS, which cannot be done while FileVault is on, and the next OS update would undo it.
2. **One permission unlocks almost everything: Full Disk Access.** Without it, `~/Library/Mail`, `~/Library/Safari`, `~/.Trash` and the per-user TCC.db all return `EPERM` (verified-locally). Per WWDC23, FDA also skips the Sonoma "access data from other apps" prompt. Per a third-party test (lapcat), FDA implies the Ventura "App Management" permission. No API requests FDA. The app can only deep-link to the pane and poll a probe. Detect FDA with a per-user probe, never with the system TCC.db (F-0001).
3. **The App Store is not viable for the full product.** Guideline 2.4.5(i) requires the sandbox, and 2.4.5(v) forbids root escalation. DTS says FDA does not bypass the sandbox and that no App Store-compliant way exists to delete root-owned apps. Ship with Developer ID, notarized, hardened runtime and no sandbox. That is what PureMac (verified-locally) and Pearcleaner (entitlements file) do. A sandboxed Lite build is possible later for the visualizer only.
4. **Root-owned leftovers need an `SMAppService.daemon` helper** (macOS 13+, needs admin approval in Login Items). `SMJobBless` has been deprecated since macOS 13 and `AuthorizationExecuteWithPrivileges` since 10.7 (SDK headers). The helper must expose typed operations, never a shell. It must validate callers with `setCodeSigningRequirement`, never by PID. Pearcleaner gets both wrong (F-0002, shell injection as root reproduced locally).
5. **Delete to the Trash with `FileManager.trashItem`, not `NSWorkspace.recycle`.** Locally, only `trashItem` writes Finder's "Put Back" record (3 of 3 runs). It returns the real destination URL (collisions get a timestamp suffix), which makes undo a single `moveItem`. On external volumes it uses `<vol>/.Trashes/<uid>`. Secure erase is not a feature on SSDs (`srm` is gone).

## Implications for macontrol

1. **Distribution:** Developer ID, notarized, hardened runtime, not sandboxed (F1, F2, C9, A10). Minimum macOS 13 is required for `SMAppService` and `setCodeSigningRequirement`. The Sonoma data-container prompt (C5) only matters if FDA is not granted. The update channel and a possible App Store Lite build belong to T-0011.
2. **Onboarding asks for one permission, FDA.** Deep link with C3's URL. Poll a tri-state probe (granted, EPERM, unknown) on the per-user TCC.db, as in F-0001. Until FDA is granted, scans still run but label protected areas "not scanned (needs Full Disk Access)" rather than showing smaller totals. Emptying or measuring the Trash needs FDA (D4).
3. **"Remove system apps" becomes "Apple apps":**
   - Group A, built into macOS (`/System/Applications`, sealed volume, or `SF_RESTRICTED`): shown read-only with the note "part of macOS, can't be removed".
   - Group B, Apple App Store apps (`_MASReceipt` plus Apple Mac OS Application Signing): removable, re-downloadable for free. Admin rights are needed because the bundle is root-owned. Offer the content libraries (GarageBand/Logic loops) as separate line items with their sizes.
   - Detection is cheap: path prefix, `statfs` read-only, `st_flags & SF_RESTRICTED`, receipt presence, signing authority (A4, A6, A8, B2).
4. **One deletion engine:** every user-owned item goes through `FileManager.trashItem` in-process. Keep the returned URL for undo; you get Put Back (D1-D3) and per-volume trash (D5) for free. `NSWorkspace.recycle` is not used (no Put Back record, possible UI, D3/D6). Permanent delete happens only on "Empty Trash" or an explicit "Delete immediately" confirmation. No secure-erase option (D7).
5. **Privileged helper (optional, installed lazily)** for root-owned items only, such as `/Library/LaunchDaemons/*.plist`, `/Library/Application Support/<vendor>` and root-owned app bundles. It uses `SMAppService.daemon`, a typed XPC API (`trash([path])`), a helper-side path validator with the same denylist, and `setCodeSigningRequirement` (E1-E4, F-0002). No shell and no AppleScript `with administrator privileges`.
6. **Protected-path denylist, enforced in the deletion engine and again in the helper:**
   - (a) Anything with `SF_RESTRICTED`, or on a read-only or sealed volume (B1-B2).
   - (b) The `rootless.conf` list.
   - (c) Curated user-data roots that look like junk but are not: `~/Library/Mobile Documents` (iCloud Drive; deleting here deletes in iCloud, unverified), `~/Library/Keychains`, `~/Library/Mail`, `~/Library/Messages`, `*.photoslibrary`, `~/Library/Containers/com.apple.*` and `~/Library/Group Containers/*.com.apple.*` data, TCC directories, `/private/var/vm`, `/.DocumentRevisions-V100`, `/.Spotlight-V100`, `/.fseventsd`, and live `/private/var/folders/*/*/{T,C}` of running apps (B4).
   - iPhone backups (`~/Library/Application Support/MobileSync/Backup`) are opt-in only, never "junk".
7. **Uninstall ordering:** quit the running app, then trash the bundle (system extensions follow, C10, unverified for third-party trashing), then leftovers, then root-owned items through the helper. App Management (C6-C8) is covered once FDA is granted (C7). Without FDA, expect a "prevented from modifying apps" notice for some bundles.
8. **Scanning:** never read file contents under iCloud-managed paths. `SF_DATALESS` marks evicted files (B2), and whether reading them triggers a download is left to T-0009.

## Decisions the user must make

1. **Distribution:** Developer ID only (recommended), or also a sandboxed App Store "Lite" build (visualizer plus user-selected folders, no uninstall of root-owned apps, no helper)?
2. **Privileged helper in v1?** With it, root-owned leftovers and App Store Apple apps can be removed from inside macontrol, at the cost of one admin approval in Login Items. Without it, those items are listed as "needs admin: reveal in Finder" and Finder asks for the password.
3. **Scope of "remove system apps":** limit it to Group B (App Store Apple apps plus their content libraries) and show Group A as protected (recommended)? Or also publish an expert guide for disabling SIP and Authenticated Root? That is not recommended: it cannot be done with FileVault on (A2) and the next OS update reverts it.
4. **Default delete behaviour:** always to the Trash (recoverable, recommended), or allow "delete immediately" for regenerable caches to save the second step?
5. **Minimum macOS version:** 13 (the floor for `SMAppService`) or 14 (Sonoma, where the container-protection model is uniform)?
6. **Spike budget for the unverified items:** whether trashing a whole notarized bundle triggers App Management without FDA (C8), and whether third-party trashing deactivates system extensions (C10). Both need a throwaway notarized app or a VM, which is suggested for M2.
