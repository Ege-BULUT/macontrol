## Summary

WinDirStat is the reference Windows disk-usage analyzer: a sortable tree, a file-type legend and a cushion-shaded treemap, now also with sunburst, flame graph, "storage analytics" (age tiers), duplicates, largest files, search, a file watcher and a permissions view. The 2.x rewrite is modern C++23 with a multithreaded scanner and an optional raw-NTFS MFT reader. Cleanup is user-driven. The user selects items and deletes them to the Recycle Bin or permanently, runs Windows maintenance shortcuts (DISM, Disk Cleanup, shadow copies, hibernate, profiles), or runs **user-defined shell command templates**. There is no built-in junk catalogue and no leftover detection.

For macontrol, the treemap renderer, the legend-to-map highlight, the command-enablement table, the batching scanner and the "unknown space" tile are worth learning from. Four weak spots became findings or evidence: hard-link attribution (F-0047), duplicate-to-hardlink replacement (F-0048), the file-type palette (F-0049), and a delete path with no protected-path guard (evidence on T-0014 / F-0024).

## Architecture

- **Model / engine.** `CItem` (`Item.h`, `Item.cpp`, `Item.Extended.cpp`) is the one tree node type for drives, folders, files and pseudo items (`<Free Space>`, `<Unknown>`, `<Hardlinks>`). The type and state live in one bitmask (`Item.h:44-84`). `CWinDirStatModel` (`WinDirStatModel.cpp`, `WinDirStatModel.Actions.cpp`) owns the root, the zoom, the extension data and every command handler.
- **Finders.** An abstract `Finder` (`Finder.h`) has three backends: `FinderBasic` (NtQueryDirectoryFile, `FinderBasic.cpp`), `FinderNtfs` (reads the `$MFT` directly with `FSCTL_GET_RETRIEVAL_POINTERS` + `ReadFile`, `FinderNtfs.cpp:162-250`) and `FinderMtp` (portable devices through the shell). The backend is chosen per queued item (`Item.cpp:1135-1138`).
- **Views.** `Views/*` are panes and `Controls/*` are the renderers: `TreeMap.cpp`, `TreeMapLayout.cpp`, `HilbertMooreTreeMap.cpp`, `Sunburst.cpp`, `FlameGraph.cpp`, `ExtensionListControl.cpp`, plus the tree and list controls.
- **UI/engine separation.** Scan threads write straight into the `CItem` tree with atomics. A tree mutation that touches a visible row is marshalled to the UI thread with `InvokeInMessageThread`. Hidden nodes are mutated in place under a shared lock (`Item.cpp:268-277, 80-87`). Per-row view state lives in a side table keyed by item, only for visible rows (`CTreeListControl::s_viewStates`, `Item.cpp:273-274`), so a hidden node carries no UI cost.
- **Command enablement is one declarative table.** Each command has flags: allowed with no selection, with many, before the scan settles, which focus, which item types, and an extra predicate (`WinDirStatModel.Actions.cpp:37-179`). For example, Delete needs a settled scan and a non-root item that has a shell identity (`:101-102`). This is a clean pattern for macontrol's menu, toolbar and context-menu state.
- **Settings.** Typed `Setting<T>` objects with min/max clamps (`Options.h:180-354`), stored in the registry or in portable INI mode.

## Scanning

- **APIs.** `NtQueryDirectoryFile` with `FileIdFullDirectoryInformation`, falling back to `FileFullDirectoryInformation` (`FinderBasic.cpp:84-101`). It uses a 4 MiB thread-local buffer for local volumes and 64 KiB for remote ones, because larger buffers break old redirectors (issue #631, `:41-53`). Fast mode reads the NTFS MFT directly (`FinderNtfs.cpp`). This is Windows-only, but the lesson carries over: "one bulk metadata call per directory, big reused buffer", which is getattrlistbulk on macOS (see T-0006).
- **Concurrency.** Each volume gets a `BlockingQueue` with N worker `std::jthread`s. N is `ScanningThreads`, default 4, range 1-16 (`Options.h:288`, `WinDirStatModel.Actions.cpp:1173-1200`). `Push` uses `push_front` and `Pop` uses `pop_front` (`BlockingQueue.h:78-128`), so the queue is LIFO and the walk is depth-first, which keeps the queue short. Workers exit when all are idle and the queue is empty (`:102-108`).
- **Batching.** `ScanBatch` collects up to 128 children or 100 ms of work before it propagates sizes, counts and extension totals up the parent chain and appends the rows (`Item.cpp:25-97`). This cuts the atomic traffic up the chain. It is worth copying.
- **Sizes.** Every item carries both logical (`EndOfFile`) and physical (`AllocationSize`) size (`Item.h:365-366`). Physical size is corrected with `GetCompressedFileSize` for sparse and compressed files, skipped on UNC paths (`FinderBasic.cpp:213-231`). Impossible allocation values from the WSL 9P redirector are dropped (`:184-211`). The map uses physical size by default (`TmiGetSize`, `Item.Extended.cpp:483-486`; `TreeMapUseLogical=false`, `Options.h:229`).
- **Hard links.** A post-scan pass per drive moves every multi-link file's bytes into a synthetic `<Hardlinks>` node and gives the real folders 0 (`Item.Extended.cpp:839-955`, `Item.cpp:386-389`). Folder scans skip the pass entirely (`Item.Extended.cpp:767-771`). **Finding F-0047** (model verified: a folder that frees 4 MiB reads 0 B). The pass also re-walks the whole drive on every refresh (`WinDirStatModel.Actions.cpp:1063-1072, 1245-1253`).
- **Clones.** Not handled: a grep for block cloning (`FSCTL_DUPLICATE_EXTENTS`, ReFS block clone) finds nothing, so shared extents are counted in full. For macOS see F-0004.
- **Progress.** The range is the volume's used bytes (total minus free) and the position is the bytes scanned so far (`Item.Extended.cpp:544-561, 1104-1111`). After hard-link adjustment the range is resynced so the bar ends at 100 % (`WinDirStatModel.Actions.cpp:1262-1272`). Folder scans have range 0, so progress is indeterminate. A per-folder "time spent" column shows where the scan was slow (`ShowTimeSpent`, `Options.h:217`; `CHILDINFO::m_tstart/m_tfinish`, `Item.h:357-358`). The PacMan animation marks folders still being read.
- **Suspend / resume / cancel.** Suspend and cancel go through the queue (`BlockingQueue.h:146-231`). Cancel throws out of `WaitIfSuspended` (`:165-169`), and blocked I/O is interrupted with `CancelSynchronousIo` on every worker (`:184-192`). Stop, suspend and resume are toolbar commands. Perf note (code-read, not measured): every directory entry takes the queue mutex 3 times, through `IsPauseOrCancelRequested` twice and `WaitIfSuspended` once (`Item.cpp:1143, 1179-1180`; `BlockingQueue.h:146-170`). macontrol should poll an atomic flag instead, because contended `pthread_mutex` on macOS is slow.
- **Memory model.** A file node is a `CItem` of about 72 bytes on x64 (vptr, parent, `m_folderInfo`, 3 atomic u64, index, type, attributes, name length; `Item.h:364-371`, `TreeListControl.h:93`). My estimate, since there is no `static_assert`. The UTF-16 name is stored inline after the object through a placement `operator new` (`Item.cpp:101-112`). Folders add a heap `CHILDINFO` holding `std::vector<CItem*>` plus 5 atomics (`Item.h:353-362`). Full paths are not stored; they are rebuilt from parents. Compare F-0041 (Radix, 943 B/node).
- **Filters and exclusions.** Hidden and system files and dirs, symlink files (excluded by default, `Options.h:180`), Dropbox-ignored streams, regex/glob include/exclude, and size and age filters (`Item.cpp:1148-1171`, `Filtering.cpp`). Cloud placeholders are skipped for duplicate hashing by default (`FileDupeControl.cpp:35`, `SkipDupeDetectionCloudLinks=true`, `Options.h:222`). Closed issue #416 (21 comments) was the scanner downloading offline OneDrive files. The macOS parallel is dataless iCloud files: never read them.

## Deletion & rules

- **Where the rules live.** There is no junk or leftover rule set. Cleanup has three kinds:
  1. Delete the selection to the Recycle Bin (`Del`) or permanently (`Shift+Del`) (`windirstat.rc:361-362`, `WinDirStatModel.cpp:499-659`).
  2. Hard-coded Windows maintenance: Disk Cleanup, Storage Sense, DISM analyze/cleanup/ResetBase, shadow copies through WMI, hibernate off, local and roaming profiles through WMI, VHDX optimize, NTFS compression, sparsify, Mark-of-the-Web removal, set dates, remove empty folders (`WinDirStatModel.Actions.cpp:314-350, 633-723, 1342-1570`).
  3. **User-defined cleanups.** These are data-driven, but the data is a shell command line: a `USERDEFINEDCLEANUP` record with title, command template, scope flags (drives, dirs, files, UNC), recurse, confirm (default **false**), show console, wait, and refresh policy (`Options.h:99-120`), stored in settings. The placeholders `%p %n %sp %sn` are replaced by raw paths and the result is run as `cmd.exe /C <line>` (`WinDirStatModel.cpp:791-842`). Paths are not quoted, and cmd expands `%VAR%` inside file names, so the user's template must quote the placeholders. This is the class of F-0002 (paths interpolated into a shell), so macontrol should not offer shell templates.
- **Trash vs rm.** Trash goes through `IFileOperation` with `FOFX_RECYCLEONDELETE | FOF_NOCONFIRMATION`, without `FOF_WANTNUKEWARNING`, plus `FOF_NO_UI` on the default path (`WinDirStatModel.cpp:611-637`). Microsoft's docs say FOF_NOCONFIRMATION answers "Yes to All" and that only FOF_WANTNUKEWARNING warns when an item is destroyed instead of recycled (learn.microsoft.com, IFileOperation::SetOperationFlags). So an item the Recycle Bin cannot hold is destroyed silently. This comes from the docs and a code read; I did not run it on Windows. Evidence posted to T-0015 (class of F-0018). Permanent delete deletes files in parallel from the **scan-time tree**, then directories bottom-up, then hands anything left over to the shell (`:547-607`). HRESULT failures are only traced (`:630`).
- **Privilege escalation.** WinDirStat relaunches itself with `runas` (`HelpersTasks.cpp:370-380`). There is an elevation prompt at start, or auto-elevate (`WinDirStat.cpp:386-474`), and `FOFX_SHOWELEVATIONPROMPT` for shell deletes. Maintenance commands are enabled only when elevated or when elevation is possible (`WinDirStatModel.Actions.cpp:83-93`).
- **Protections.**
  - Good: Delete is disabled until the scan settles, and never works on the scan root (`WinDirStatModel.Actions.cpp:101-102, 164`).
  - Good: the confirmation dialog lists every path (`WinDirStatModel.cpp:505-513`).
  - Good: "Remove empty folders" skips reparse points, re-checks the attributes right before acting, and uses a non-recursive `RemoveDirectory`, so the OS refuses a folder that is not empty (`WinDirStatModel.Actions.cpp:1488-1544`). This is a good last line of defence to copy.
  - Weak: there is **no protected-path list**. The permanent-delete warning can be turned off for good with "Don't show again" (`WinDirStatModel.cpp:500-519`). `DeleteFileForce` clears READONLY, HIDDEN and SYSTEM without telling the user (`HelpersTasks.cpp:257-263`). Its delete-on-close fallback opens the path without `FILE_FLAG_OPEN_REPARSE_POINT` (`:267-269`). By code read, that would delete a symlink's target, but only if the user has turned symlink files back on. Evidence posted to T-0014 (class of F-0024).
- **Dry run.** There is none. There is no journal and no undo beyond the Recycle Bin.
- **Duplicates → hard links.** Staged hashing (size, then XXH3-64 over 4 KiB, 1 MiB, then the whole file) builds the groups (`FileDupeControl.cpp:52-120`, `HelpersTasks.cpp:773-778`). "Deduplicate with hardlink" replaces copies with hard links without re-reading them, and drops failures (`WinDirStatModel.Actions.cpp:1401-1436`, `HelpersTasks.cpp:688-704`). **Finding F-0048**, measured on APFS: the replaced file took the kept file's mode 644 instead of 600, and a later edit to one path changed both. The detector had false duplicates in #175, #267 and #368, and a group-merge bug in #655 that was fixed in 860d840 on 2026-09-05.

## UI

- **Rendering.** The treemap is software-rendered. The CPU writes 32-bit pixels into a DIB, drawn straight into the target DIB section when possible (`TreeMap.cpp:707-732`). It is rendered synchronously on the UI thread (the wait cursor at `GraphView.cpp:122-150`), cached as a bitmap, and hover, selection and extension highlights are drawn as overlays on the cached bitmap, so moving the mouse never re-renders (`GraphView.cpp:103-161`, `TreeMapView.cpp:98-168`). The rows of a big cushion are rendered in parallel only when a leaf is at least 512k pixels (`TreeMap.cpp:1056-1068`).
- **Cushion algorithm (van Wijk).** Each node carries 4 surface coefficients. `AddRidge` adds a parabolic ridge of height `h` per level, and the height shrinks by `scaleFactor` per depth (`TreeMap.cpp:750-757, 1071-1087`). Each pixel's normal is `(-(2·s0·x+s2), -(2·s1·y+s3), 1)`, and brightness is `Ia + (1-Ia)·max(0, n·L)` (`TreeMap.cpp:1006-1054`). The light vector is normalised with lz = 10 (`:436-451`). Defaults: H 0.38, F 0.91, Ia 0.13, light (-1, -1), brightness 0.88 (`TreeMap.h:337-352`). There are five presets: Classic, Calm, Flat, Pastel, HighContrast (`TreeMap.cpp:268-307`). This maps directly to a Metal fragment shader: pass the 4 coefficients and a colour per leaf instance, and it costs 1 sqrt per pixel on the GPU.
- **Layouts.** `Rows` (KDirStat, min aspect 0.4), `Squarified`, `Hilbert` and `Moore` (`TreeMapLayout.cpp:33-209`). Children under a pixel get empty rectangles and are skipped (`TreeMap.cpp:775-779`). The Hilbert and Moore curves keep sibling order spatially stable, so a rescan or delete moves tiles less.
- **Hit-testing.** Geometry is kept outside `CItem` in `m_visibleItems`. A 16 px grid index stores only the area each parent owns exclusively, so storage does not multiply with depth (`TreeMap.cpp:477-620, 873-904`). This is a solid design for macontrol's hover and click on big maps.
- **Interaction.** Click selects and syncs to the tree. Zoom in/out/reset works on a drill-down root with a coloured zoom frame (`TreeMapView.cpp:70-96`, `WinDirStatModel.Actions.cpp:422-452`). "Select parent" and "Reselect child" keep a stack (`:779-798`). Clicking an extension in the legend highlights every tile of that type (`TreeMapView.cpp:98-115`). The context menu offers open, select in Explorer, Explorer context menu, copy path, console/PowerShell here, properties, move, delete. The sunburst shows omitted children as "a muted residual sector that preserves the parent's proportions" (`Sunburst.cpp:260`), which is the same idea as F-0016's "N smaller items" tile. The flame graph has a sticky breadcrumb row (`FlameGraph.cpp:65-90`). Storage Analytics groups data into Hot, Cool, Cold and Archive tiers by age (`Views/StorageAnalyticsView.cpp:90-130`), a useful view for "old stuff you could delete".
- **Pseudo tiles.** `<Free Space>` and `<Unknown>` (used space minus scanned bytes) can be shown as tiles. Both are off by default (`Options.h:215, 221`). "Unknown" is the honest answer to "where did the rest go", which on macOS means purgeable space, snapshots and System Data (see F-0005).
- **Limits.** The map and the other graphs draw nothing until the whole scan is done (`IsReadyToDraw` needs `root->IsDone()`, `GraphView.cpp:85-89`), and they dim during any refresh (`WinDirStatModel.Actions.cpp:1034-1035`). A user waits for the full scan before seeing a single tile. macontrol should draw progressively; that is a feature gap, not a defect, so it is noted here rather than filed. The file-type palette has poor CVD distinguishability, and every rank from 18 down shares one gray. **Finding F-0049** (measured). The folder-branch palette in the same codebase is close to Okabe-Ito (`TreeMap.cpp:105-108`).
- **Visual quality.** It is dense and functional. Dark mode, high DPI and 25 languages are supported (25 files in `res/langs`). The Win32 look is dated, which is where macontrol can clearly beat it.

## Tests & quality

- **Tests.** `tests/Test-WinDirStat.ps1` (15,252 lines) is a black-box end-to-end harness. It covers headless CLI scans compared against a PowerShell ground truth; enumeration parity across path spellings (`\\?\`, UNC, subst, junction, symlink) and across FAT32, ReFS and NTFS; UI automation of the file operations, checked against the real file system; MTP; permissions export; and command-line parsing (`Test-WinDirStat.ps1:1-45`). The reparse and file-system suites format two scratch drives under 4 GB and refuse C: (`:34-42`). There are no C++ unit tests. CI (`.github/workflows/*`) only publishes to winget and runs no tests. Worth copying: "one known tree scanned through many root spellings, each diffed against an independent ground truth", which is already our research/bench approach.
- **Quality.** Modern C++23 (ranges, `std::jthread`, `std::execution::par`), RAII `SmartPointer`, asserts on layout invariants (`TreeMapLayout.cpp:187-189`, `TreeMap.cpp:637-657` in debug), and PGO training scripts (`tests/Build-PgoTrainingProfiles.ps1`). Comments explain the why. Some of it is AI-assisted: issues #655 and #634 quote "Google AI Mode" and Gemini analyses.

## Known problems

From open issues (`gh api .../issues?state=open`, 36 open) and the code:
- Hard links are attributed to a synthetic node instead of their folders. #448 (9 comments) asked for in-place attribution and was marked "not planned". Filed as F-0047.
- Dedupe: groups were merged (#655, fixed 2026-09-05), NTFS's 1024-link limit is hit silently (#655), false duplicates shipped earlier (#175, #267, #368). Filed as F-0048.
- A permanent delete of 160k items showed a modal "Progress" dialog for about 3 minutes that could not be cancelled (#663). The shell delete runs in a CProgressDlg with no cancel path (`WinDirStatModel.cpp:636-637`).
- Sorting is unstable (#654). Free space is not visualised for mount points (#651). WSL `\\wsl$` scans are unreliable (#648). The registry is written in portable mode (#640, 17 comments). People ask to always run elevated (#652).
- Past performance issues: laggy UI or 10 fps after a scan (#151, 37 comments), a freeze after scanning (#143), constant CPU use (#32). All are closed.
- Silent trash-to-permanent delete through the IFileOperation flags (docs plus code read, see above).

## Open questions

- Is the per-entry queue-mutex polling (`Item.cpp:1143, 1179-1180`) measurable at 16 threads? Not measured; Windows only. Our Swift scanner should use an atomic flag anyway. Handed to T-0006 as a design note, not a benchmark.
- Does the trash path really destroy items the Recycle Bin cannot hold, with no prompt? This is from the docs plus a code read and needs a Windows machine to confirm. Not relevant to macOS behaviour, but it shows the "trash-or-fail" rule we need (F-0018).
- WinDirStat's scan throughput and memory on a million-file tree are unmeasured here; it cannot run on macOS. The per-node byte estimate (about 72 B + UTF-16 name) comes from reading the struct layout, not from a `sizeof`.
- The LCA rule in F-0047 needs a decision on how to draw a "shared by N links" tile when the LCA is far above the links, for example at the volume root. Proposal: draw it at the LCA folder and badge each link row. UI owner: T-0007.
- Should macontrol offer a "reclaim duplicates by cloning" action at all (F-0048)? That is a product decision for T-0008.
