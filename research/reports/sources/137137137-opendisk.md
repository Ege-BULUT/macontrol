## Summary

OpenDisk is a disk-space visualizer only, positioned as a free alternative to DaisyDisk. It draws a sunburst next to a Finder-style sortable list, fills both in live while the scan runs, and has a DaisyDisk-style "Collector" tray for deleting what you gather. It has no app uninstaller, no leftover finder and no rule engine. The cleanup side is one hard-coded list of 23 cache folders, shown as a "Purgeable Space" row.

The engine is the reason to study it. It is small, well commented, MIT-licensed and portable (engine files import only `Darwin`, `Foundation`, `Synchronization` and `CoreServices`). It has four parts:
- a fixed pool of blocking `getattrlistbulk` workers;
- a struct-of-arrays tree with `Int32` links and no stored paths;
- a correct composition of the boot volume group (System + Data via firmlinks, with helper volumes grafted in);
- a persistent scan cache that replays the FSEvents journal, so rescans re-read only the directories that changed.

The code comments record the author's own measurements, including negative results. One example: `searchfs` is about 2x slower than parallel `getattrlistbulk` on APFS, so it is used only on HFS+ (`CatalogScanner.swift:13-17`, `ScanEngine.swift:385-400`).

What I verified here (probes compile OpenDisk's own, unmodified files):
- The full-scan engine is deterministic and matches du and dua on the shared fixture: 2,359,623,680 B in 3 of 3 runs, 311,365 nodes, 35 MB max RSS, about 3.3 s with 3 workers at load average ~18 (this is not a benchmark).
- It misses the fixture's PATH_MAX-deep subtree (8,417,280 B), which is F-0008.
- The incremental path, the one behind the README's "20-28x faster rescans" claim, has two defects I reproduced: it re-counts hard links (F-0037) and it never frees replaced nodes (F-0038).
- The delete guard can be bypassed through the `/System/Volumes/Data` alias (F-0039).

The README's scan-time claims (1 TB in 17 s against 37 s for DaisyDisk, rescans 20-28x faster) are the author's own and **unverified**.

## Architecture

```
OpenDisk/
  App/        OpenDiskApp (SwiftUI App), MoveToApplications, SoftwareUpdater (Sparkle)
  Models/     FolderItem, ChartItem, Collector (@Observable, @MainActor), CollectedFile (Transferable JSON),
              DeviceInfo, HiddenSpace (CleanableCacheCatalog), ScanProgress
  Services/   DiskAnalyzer (view model), DeviceMonitor, FullDiskAccess, ProtectedPaths, ScanAccess (MAS bookmarks), UserHome
    Scanning/ ScanEngine (strategy, streaming), TraversalScanner, CatalogScanner, FileTree, ScanCache,
              IncrementalUpdater, ScanMetrics, DiskScanning (protocol)
      SystemInterop/ BulkDirectoryReader (getattrlistbulk), SearchFS (searchfs), FSEventsChangeJournal, VolumeAttributes
    Search/   SearchIndex (memmem over a name blob)
  Views/      Analysis/, Charts/ (RingsChartView, RingsChartLayout, ChartPalette, ChartHoverTip), Components/, Main/, Settings/
```

- **UI and engine are separated by a protocol and value types.** `DiskScanning.scan(path:onEvent:) async -> ScanResult` (`Services/Scanning/DiskScanning.swift:43-56`) is the only surface. Events are `.progress(ScanProgress)` every 33 ms and `.partial(PartialScanResult)` with a monotonically increasing sequence. `FileTree` is a `Sendable` struct handed to the main actor whole. `DiskAnalyzer` (`@MainActor @Observable`) injects the scanner, which lets tests pass fakes (`DiskAnalyzer.swift:113-115`, `OpenDiskTests/DiskAnalyzerTests.swift`).
- **Blocking work never runs on the Swift cooperative pool.** It runs on custom `DispatchQueue`s at `.userInitiated`, and the comments explain the priority-inversion fix (`ScanEngine.swift:180-205`, `TraversalScanner.swift:146-160`). Commit 3ac9188 fixed an inversion flagged by the Thread Performance Checker.
- **Process-wide tuning:** `setiopolicy_np(IOPOL_TYPE_DISK, IOPOL_SCOPE_PROCESS, IOPOL_IMPORTANT)` and `RLIMIT_NOFILE` raised to 65,536 (`ScanEngine.swift:92-99`).

## Scanning

**APIs**
- `getattrlistbulk` with `ATTR_CMN_RETURNED_ATTRS|NAME|OBJTYPE|FILEID`, `ATTR_DIR_MOUNTSTATUS` and `ATTR_FILE_LINKCOUNT|ALLOCSIZE`. Each worker has its own 256 KB buffer (`SystemInterop/BulkDirectoryReader.swift:47-49, 84-99`).
- The parser walks a running offset gated on the returned-attributes bitmap and validates every record length against the buffer (`:105-122, 141-227`).
- Directories are opened with `open(path, O_RDONLY|O_DIRECTORY|O_NOFOLLOW)`, and `fstat` checks `st_dev` against an allowlist (`:75-82`).
- `searchfs(2)` is declared through `@_silgen_name("searchfs")` because it has no public prototype (`SearchFS.swift:14-22`). It matches everything with an owner-id range of [0, UINT32_MAX] (`:189-195`). After EBUSY it restarts up to 3 times, rolling back its metrics (`:139-175`, `CatalogScanner.swift:59-92`). It is used only when the root is a volume root, the filesystem type is `hfs` and `VOL_CAP_INT_SEARCHFS` is set (`ScanEngine.swift:255-259`). `CatalogTreeBuilder` rebuilds the tree from `(fileID, parentID)` pairs, and orphans attach to the root (`CatalogScanner.swift:106-193`).

**Concurrency**
- A fixed pool of blocking workers shares one LIFO stack guarded by a `Mutex`. A `DispatchSemaphore` parks idle workers, and a pending-directories counter decides termination: the last worker out flips `isDrained` and starts a wake-up cascade (`TraversalScanner.swift:51-104`).
- Worker counts are `min(5, max(3, ncpu/4))` for subtrees and `min(8, max(4, ncpu/2))` for volumes. The comment records the measurements behind them: ~/Library (900k items) took 2.1 s with 4 workers, 3.1 s with 8 and 11.8 s with 32; the 4M-item Data volume took 12.6 s with 8 workers and 19.8 s with 16, on a 16-core machine (`:25-41`). These figures are theirs and unverified.
- One global `Mutex<FileTree>` is taken once per directory to append all its children (`:229-251`).
- The sibling helper volumes (Preboot, VM, Update and so on) are scanned one after another, never in parallel, "so reader concurrency never exceeds one worker pool" on an APFS container (`ScanEngine.swift:477-496`).

**What sizes mean**
- Sizes are allocated bytes only (`ATTR_FILE_ALLOCSIZE`). There is no logical/apparent mode.
- Directories contribute 0 of their own.
- Hard links are counted once per `(st_dev, fileID)` on a full scan (`TraversalScanner.swift:106-111, 204-223`). HFS+ catalog records are deduped the same way (`CatalogScanner.swift:137-152`). The incremental path loses this (F-0037, below).
- APFS clones are counted at full size each time. There is no `ATTR_CMNEXT_CLONEID` or `PRIVATESIZE` (grep finds no `clone` anywhere). This is the F-0004 class.
- APFS snapshots and the purgeable pool are not measured at all (see Deletion).
- Symlinks are listed as files with their own allocated size and never followed.
- Names of 1,024 bytes or more are dropped (`BulkDirectoryReader.swift:156`).
- A `getattrlistbulk` error in the middle of a directory keeps what was already parsed and does not flag the directory as unreadable (`:105-109`).

**Volume boundaries (a good answer to F-0031)**
- Scanning "/" is a single traversal of "/" with the System and Data `st_dev` allowlisted (`ScanEngine.swift:370-383, 453-474`).
- Every child directory with a nonzero `ATTR_DIR_MOUNTSTATUS` becomes an empty stub and is never entered. That covers `/System/Volumes/Data`, the `/Volumes` alias of the boot volume, Time Machine snapshot mounts and automount triggers. The comment explains why `st_dev` alone is not enough (`BulkDirectoryReader.swift:18-25, 92-96, 192-207`).
- Helper volumes under `/System/Volumes` are then scanned and merged in place (`ScanEngine.swift:506-533`), and the `/Volumes` stubs are removed from "/" (`:529`).
- Documented omission: Data-volume housekeeping directories at its own root (`.Spotlight-V100`, `.fseventsd`) are skipped (`:465-468`). That is part of the F-0005 class.

**Paths and depth**
- Workers build full path strings (`directoryPrefix + name`, `TraversalScanner.swift:225, 241`) and `open()` them, so subtrees deeper than PATH_MAX are unreadable.
- Verified on `research/bench/fixtures/tree`: OpenDisk totals 2,359,623,680 B against 2,368,040,960 B visible. The missing 8,417,280 B is `pathmax/`, which is F-0008.
- The scan counts those directories as `unreadable=2`, but the UI shows that count only when the whole result is empty (`DiskAnalysisView.swift:649`). In a normal scan they are silent.

**Progress, streaming and cancellation**
- `ScanMetrics` holds counters under a `Mutex` and is updated once per directory (`ScanMetrics.swift`). A progress task emits every 33 ms, skipping no-op events (`ScanEngine.swift:114-125`).
- Partial snapshots:
  - A `PartialResultAssembler` collects thread-safe providers and runs the same composer as the final result, so a live view is "a smaller version of the eventual result" (`ScanEngine.swift:16-48`).
  - Each snapshot costs a copy-on-write copy of the whole tree plus an O(n) roll-up, and the next worker mutation pays the duplication under the tree lock. The cadence backs off to `max(500 ms, 8 x assembly time)`, capped at 15 s (`:71-88, 133-155`).
  - The author documents this trade-off. On multi-million-node scans, late snapshots are up to 15 s apart. Hypothesis, not measured here: an append-only chunked arena would make snapshots O(1) and remove the CoW stall.
- Cancellation is a relaxed `Atomic<Bool>` polled once per directory and set from `withTaskCancellationHandler` (`ScanEngine.swift:9-14, 163-170`).

**Memory model**
- `FileTree` stores `nodes: [Node]` and `names: [String]` side by side. `Node` holds `Int64 size`, the `Int32` links parent, firstChild and nextSibling, and a `Bool` (24 B stride). There are no paths, and a path is rebuilt from the parent chain on demand (`FileTree.swift:14-32, 208-219`).
- Measured: 35.3 MB max RSS and a 31.2 MB peak footprint for 311k nodes, process baseline included (`/usr/bin/time -l`).
- Other operations:
  - Children are a singly linked sibling list, sorted per view on demand (`:135-140`).
  - Roll-up is iterative and guarded by a visited bitmap (`:273-302`).
  - `merge` joins trees by name at firmlink merge points (`:319-347`).
  - Deserialization checks the range of every link, so a corrupted cache cannot crash the app (`:411-482`).

**Incremental rescans** (the headline feature)
- `ScanCache`:
  - Format: binary `DMT2` tree plus a header holding format version, FSEvents event ID, `st_dev` and root path. The file is `~/Library/Caches/<bundle>/ScanCache/<fnv1a(root)>.dmscan`.
  - Reads memory-map the file. Writes go to a temp file that is swapped in atomically.
  - Pruning keeps at most 8 files and 4 GB (`ScanCache.swift:47-78, 82-120, 128-163, 168-177`).
- `FSEventsChangeJournal`:
  - It replays from the saved event ID until `HistoryDone`.
  - It treats `EventIdsWrapped`, `UserDropped`, `KernelDropped` and `RootChanged` as unreliable, gives up above 40,000 changed directories and bails early above 160,000 raw events (`FSEventsChangeJournal.swift:24-26, 53, 137-169, 222-233`).
  - The time budget is `clamp(cacheBytes / 10 MB / 5, 1 s, 4 s)` (`ScanEngine.swift:346-358`).
  - Verified here: the journal reports firmlinked paths (`/Users/...`, `/private/tmp/...`), not `/System/Volumes/Data/...`. So a "/" rescan resolves the changes correctly (`research/bench/137137137-opendisk/incremental_probe.swift`, both runs).
- `IncrementalUpdater`: each changed directory is re-listed shallowly. Surviving subdirectories keep their subtrees, and new ones get a fresh subtree scan. `MustScanSubDirs` paths are rescanned whole (`IncrementalUpdater.swift:17-176`).
- The cached tree is displayed at once as the first partial snapshot, before the replay finishes (`ScanEngine.swift:289-323`).
- Verified defects:
  - **F-0037:** splices add every hard link at full size, and the inflated sizes are saved into the cache. A 9,207,808 B fixture read 17,600,512 B after one splice and 25,989,120 B after a second, against 9,211,904 B from a fresh scan.
  - **F-0038:** replaced nodes are never freed. After 10 splices the tree had 2,225 nodes with 206 reachable, and the cache was 10.7x the size of a fresh one.
- Unverified gap: the cache is keyed by `st_dev` and path, not by volume UUID (`ScanCache.swift:72-76`). F-0017's "after" proposes `FSEventsCopyUUIDForDevice`. I did not test whether a reformatted disk mounted at the same path with the same `st_dev` could revive a stale tree.

## Deletion and rules

- **Where the targets come from.** Items reach the Collector by in-app drag or by "Add to Collector" in the context menu (`Views/Components/FileActionsMenu.swift`, `RingsChartView.swift:61-70`).
  - The only "rules" are `CleanableCacheCatalog.locations`: 23 hard-coded Swift paths covering Homebrew, npm, Yarn, pnpm store, pip, Cargo, Go, Gradle, CocoaPods, Composer, Xcode DerivedData, DeviceSupport and Archives, Playwright, Puppeteer, Chrome, Safari, Hugging Face, torch, `~/Library/Logs`, `~/.Trash` and `/Library/Caches` (`Models/HiddenSpace.swift:21-64`).
  - The list is not data-driven. The UI calls it "Purgeable Space", but it has nothing to do with APFS purgeable space; the code comment says so (`DiskAnalyzer.swift:248-253`), the README does not.
  - Dragging that one row collects every folder on the list (`DiskAnalysisView.swift:577-585`). That includes **Xcode Archives** (dSYMs for shipped builds) and the **Trash**, although the catalog's own comment says "Deliberately conservative ... nothing whose loss changes user-visible state" (`HiddenSpace.swift:18-20`). This is the F-0027 class; see the comment on T-0022.
- **Collector model.**
  - Paths are de-duplicated and kept disjoint: collecting a folder drops its collected descendants, and a child of a collected folder is a no-op (`Collector.swift:60-75`).
  - Collection edits (not deletions) have a 50-step undo (`:36-42, 107-123`).
  - Synthetic `::` rows and missing paths are refused.
  - Tests cover all of this (`OpenDiskTests/CollectorTests.swift`, 12 cases).
- **Trash vs rm.**
  - Deletion is **permanent**: `FileManager.default.removeItem(atPath:)` per item, in `Task.detached` (`Collector.swift:142-182`). The comment explains that Trash was rejected because the "freed" figure would not be real.
  - The confirmation is a native `confirmationDialog`: "This permanently deletes the collected items and can't be undone." (`CollectorBar.swift:104-116`).
  - The "freed" figure is the scan-time size, not measured (`Collector.swift:171`).
  - After a delete, the root is rescanned through the incremental path (`DiskAnalysisView.swift:568-575`).
  - This is the F-0012 class (no quarantine) and part of F-0018 (freed size never checked).
- **Privilege escalation:** none. There is no helper and no root; deletes run as the user.
- **Protections.** `ProtectedPaths.reason(for:)` is a string blocklist (`Services/ProtectedPaths.swift:9-46`), and the context menu disables "Add to Collector" for protected paths (`FileActionsMenu.swift:19`).
  - Blocked: `/`, 19 system roots, `$HOME`, `~/Library`, direct children of `/Users`, `/Volumes` and `/System/Volumes`, and any ancestor of those.
  - Not blocked: `~/Documents`, `~/.ssh`, `~/Library/Keychains` (probe output). That is the F-0024 class.
  - Firmlink alias spellings pass: `/System/Volumes/Data/Users/<me>` is the same inode as `~` and is ALLOWED. This is **F-0039**.
- **Dry run:** the Collector tray is the review list. Nothing else previews or simulates a delete.

## UI

- SwiftUI throughout, with native `.searchable`, `confirmationDialog`, `ContentUnavailableView`, a Quick Look sheet on the spacebar (`DiskAnalysisView.swift:160-170`) and a toolbar Refresh (⌘R).
- **Sunburst:**
  - It is two stacked `Canvas` layers. The static layer holds every sector, border and curved label; it is `Equatable` and repaints only when the layout changes. A thin overlay draws the hover highlight and tip (`Views/Charts/RingsChartView.swift:1-35`).
  - Hit-testing converts the pointer to polar coordinates and scans the segment list linearly (`RingsChartLayout.swift:45-60`). That is fine because segments are capped: 5 rings, items under 0.15% of the root dropped, sweeps under 0.03 rad not drawn (`ChartItem.swift:43-48`, `RingsChartLayout.swift:14-15`).
  - The layout model "follows GNOME baobab's chart; the implementation is original Swift" (`ChartItem.swift:6-9`). Baobab is GPL, so treat this as a design reference only (for T-0003).
  - Interaction: a click on a directory drills in, and a click on the centre goes up. You can drag a slice to the Collector, and the context menu offers Add to Collector, Show in Finder and Copy Path. The chart and list share one sort order by construction (`FileTree.swift:131-140`).
  - VoiceOver sees an `accessibilityChildren` list of the segments (`RingsChartView.swift:72-121`).
- **List:**
  - Finder-style sortable columns and breadcrumbs. The rows reuse the same payload types as the chart for dragging.
  - An instant skeleton shows the root's top-level names from one shallow read before any sizes arrive (`DiskAnalyzer.swift:168-177, 531-594`).
  - Final results hide items of 1 KB or less (`:24`).
  - At every level below the root only the **largest 100 children** are materialized, with no "N more" row (`DiskAnalyzer.swift:18-20, 496-501`). This is the F-0016 class, milder than Mole's 30. Search still reaches every node.
- **Search:**
  - The index holds case-folded, NFC-composed names in one NUL-separated blob, swept with `memmem` in parallel chunks. Results are capped at 500, but the true match count is reported (`Services/Search/SearchIndex.swift:1-60`).
  - The index is rebuilt after every finished scan, and mid-scan searches use the partial tree (`DiskAnalyzer.swift:423-492`).
- **Devices:**
  - The picker lists "/" plus browsable external volumes (`Services/DeviceMonitor.swift:25-72`).
  - "Available" is `volumeAvailableCapacity`, not `...ForImportantUsage` (`:77-95`), so it can read lower than Finder's figure. Unverified on this Mac.
  - A "/" scan is gated on Full Disk Access, with Open Settings and Quit & Reopen buttons (`DiskAnalyzer.swift:126-134`, `DiskAnalysisView.swift:640-648`).
- **FDA probe:** `FullDiskAccess.isGranted` is derived from inket/FullDiskAccess (MIT). The first probe that exists decides: readable means granted (`Services/FullDiskAccess.swift:7-9, 25-42`). The first path it tries is `~/Library/Containers/com.apple.stocks`. The T-0010 lesson notes that reading other apps' containers can show a prompt. Whether this path prompts on macOS 26 is **unverified**.

## Tests and quality

- There are 65 `@Test` functions in 9 files (some take `arguments:`) plus 1 XCUITest launch test. They cover FileTree (round-trip, malformed blobs, cycles, merge), TraversalScanner (sizes, hard links, partial snapshots, cancellation), CatalogTreeBuilder, Collector, ProtectedPaths (14 tests), SearchIndex, the chart model and layout, the analyzer with a fake scanner, and formatters.
- **Nothing tests** `IncrementalUpdater`, `ScanCache`, `FSEventsChangeJournal` or the "/" composition in `ScanEngine`. Those are the parts behind the headline claims, and they are where both verified engine defects live.
- I did not run `xcodebuild test`: it needs Xcode, and the machine is loaded. The engine probes compile the source files directly with `swiftc -swift-version 6` and build clean.
- Code quality is high:
  - Comments explain why, measurements are recorded, and negative results are written down.
  - Errors on the `searchfs` path use typed throws.
  - Sibling walks are bounded against corrupted caches (`FileTree.swift:151-168`).
  - Concurrency hazards are handled deliberately: QoS floors, exactly-once continuation latches in the journal (`FSEventsChangeJournal.swift:42-96`).
- The commit history is thin (messages like "asd", "lol", "updates"), mostly from one author.

## Known problems

1. Incremental rescans re-count hard links, and the cache keeps the inflated sizes (**F-0037**, verified).
2. Incremental rescans never free replaced nodes, so the tree and cache grow on every rescan (**F-0038**, verified).
3. The delete guard is bypassed through `/System/Volumes/Data/...` alias paths, followed by a permanent delete (**F-0039**, verified). A small blocklist also lets `~/Documents` and `~/.ssh` through (F-0024 class).
4. PATH_MAX-deep subtrees are dropped, 8,417,280 B on the fixture, and the unreadable count shows only when the view is empty (F-0008 class, verified).
5. APFS clones are counted at full size (F-0004 class, from reading the code: `ATTR_FILE_ALLOCSIZE` only).
6. Deletes are permanent, and "freed" is the scan-time size (F-0012, F-0018 classes).
7. The "Purgeable Space" row is misnamed: it is not the APFS purgeable pool. One drag collects Xcode Archives and the Trash (F-0027 class).
8. Drill-in levels show the top 100 children with no remainder row (F-0016 class).
9. Snapshot cost is O(n) CoW under the scan lock, so late snapshots on huge scans are up to 15 s apart (documented by the author; cost not measured here).
10. The cache is identified by `st_dev` and path, not volume UUID (unverified risk).
